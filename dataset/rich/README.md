# Rich synthetic transaction dataset (Phase 1)

**Everything in this folder is synthetic.** IP addresses are randomly assigned synthetic values sampled from public ranges; they are not
observed traffic and no real person or network did anything. Ports, countries and ASNs describe those synthetic addresses.
Country and ASN come from a lookup in the DB-IP Lite databases (IP geolocation by DB-IP.com, CC BY 4.0, see `data/geoip/ATTRIBUTION.txt`).

Generated by `generate_rich_dataset.py` (seed 149, deterministic) from `dataset/synthetic_bitcoin_transactions.csv`, which it only reads.

| File | Content |
|---|---|
| `synthetic_rich_transactions.jsonl` | primary file: one record per existing transfer (5,000), same order and same ids as the backend importer |
| `synthetic_rich_transactions.csv` | the same records; the four list fields are JSON arrays inside the cells |
| `sample.json`, `sample.jsonl`, `sample.csv`, `sample.xml` | the same 20 records in each of the four supported formats (for tests and docs) |
| `ground_truth_address_owner.csv` | address → owning legacy wallet. **For validation only.** Nothing in the backend or the analysis reads it |

## Record fields
`timestamp` (UTC), `txid` (64 hex), `legacy_transaction_id` (`syn-000001`…, the id the backend importer already assigns), `sender_wallet`,
`receiver_wallet`, `amount_btc`, `fee_btc`, `script_type` (p2pkh, p2sh, p2wpkh, p2wsh, p2tr), `input_addresses[]`, `input_amounts[]`,
`output_addresses[]`, `output_amounts[]`, `src_ip`, `dst_ip`, `src_port`, `dst_port`, `geo_country`, `asn`, `asn_org`.

**Later detectors must not use `sender_wallet`, `receiver_wallet`, `amount_btc` or the ground-truth file.** They exist only to feed the
existing wallet-level pipeline its flat view, and using them would give away the answer that address-level analysis is meant to find.
(`amount_btc` is the payment to the receiver: it equals exactly one output amount. It is the one field added to the field list of the
phase specification, because the flat view needs it and the payment output is otherwise not identifiable.)

## Design
- Addresses are opaque synthetic ids (`s1…` p2pkh, `s3…` p2sh, `sy1q…` p2wpkh/p2wsh, `sy1p…` p2tr), shuffled, not derived from wallet numbers.
  Each wallet owns 1–4 addresses (2–4 if it ever sends with change).
- Value balance is exact in satoshis: `sum(inputs) = sum(outputs) + fee`. There is no UTXO ledger: inputs are not linked to earlier outputs.
- The flat view is reproduced exactly: (timestamp, sender wallet, receiver wallet, `amount_btc`, number of inputs, number of outputs) equals the
  original transfer for all 5,000 records. A repeated input address means several coins spent from one address.
- The payment goes to an address of the receiver; every other output is change to an address of the sender that is not spent in that
  transaction (the least recently used one first).
- About 17% of transactions spend 2–3 different addresses of the same sender wallet.
- Network flow: each wallet has 1–3 client IPs (about 15% of wallets share an IP with another wallet); `dst_ip` is one of 8 synthetic node IPs;
  `src_port` is ephemeral; `dst_port` is 8333 in about 90% of records.

## Importing
```powershell
.\.venv\Scripts\python.exe -m backend.cli import-rich dataset\rich\synthetic_rich_transactions.jsonl
.\.venv\Scripts\python.exe -m backend.cli import-rich dataset\rich\sample.xml --format xml
```
or `POST /api/import/rich?format=csv|json|jsonl|xml` with the file as the request body. Records are attached to the existing transactions
(the flat transactions are not duplicated); importing again changes nothing.
